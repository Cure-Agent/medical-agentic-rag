# problem — 문제 분석부터 머지까지 (하네스 중립 명세)

운영 중 발생한 문제를 분석해 해결책을 제시하고, 사용자가 선택한 해결책을 구현해 `main` 머지까지 완료한다.

> **이 파일은 하네스 중립 「진실의 원천」이다.** 직접 실행 대상이 아니라 진입 어댑터를 통해 실행된다:
> - Claude Code → `.claude/commands/problem.md`
>
> 하위 절차는 다른 중립 명세를 호출한다: 테스트 동결은 `automation/freeze.md`,
> PR·머지는 `automation/ship.md`(→ `automation/pipeline.md`).

## 이 문서의 위치 — 운영 변경의 단일 진입점

**운영 중 변경은 무조건 여기서 시작한다.** `/implement`는 스펙이 이미 존재하는 계획된 스텝의
진입점이지, 사람이 고르는 갈림길이 아니다.

그 이유는 **버그 리포트 시점에는 원인을 모르기 때문**이다. "근거가 있는데 기권한다"가 점수 게이트
컷 문제인지 answerer의 구조화 출력 문제인지는 진단해봐야 안다. 그런데 하네스 선택은 그 답에
의존한다 — 따라서 **라우팅은 진단 뒤(Phase 1.5)에 기계적으로 판정**하며, 사람이 사전에 고르지 않는다.
원칙의 원본은 cure-agent-be `docs/architecture.md` §15 「5단계 이후 작업 규칙 (SDD)」다.

> **이 레포의 승격은 BE 레포를 거친다.** 스펙은 여기 없다(`/implement` Phase 0) — `docs/specs/`는
> BE 레포에 있다. 따라서 게이트가 승격을 판정해도 **이 세션이 스펙을 쓸 수 없다.** 승격은 「진단
> 결과를 BE 세션의 `/spec`에 넘기는 것」이며 그 형식은 「승격 핸드오프」가 정한다. 넘긴 뒤 이 절차는
> 끝나고, 스펙이 착지하면 `/implement <번호>`가 **새로 시작**한다 — 이어받지 않는다.

## Preflight

1. `gh auth status` — 인증 실패 시 **중단**.
2. `git fetch origin main` — 이후 모든 비교는 **`origin/main` 기준**이다. 로컬 `main`은 뒤처져 있을 수 있다.
3. `git status --porcelain` — 비어 있지 않으면 **이월 변경을 stash로 분리**한다:
   - `git stash push -u -m "problem-preflight-stash"` (untracked 포함), `HAS_STASH=true`
   - **이 변경이 이번 문제와 관련 있는지 사용자에게 확인한다.** `automation/pipeline.md` Step 1이
     `git add -A`로 워킹 트리를 통째로 쓸어담으므로, 분리하지 않으면 무관한 변경이 이번 PR에 그대로
     따라 들어간다.
     - **관련 있음** → Phase 3에서 브랜치 생성 직후 `git stash pop`으로 복원해 WIP 커밋으로 승격한다.
     - **무관함** → stash에 **둔 채로** 전 Phase를 진행하고, Phase 6의 머지 성공 후 복원한다.
       stash 상태가 워킹 트리를 clean하게 유지하므로 병렬 워크트리 통합(cherry-pick)에도 유리하다.
4. `git checkout main && git pull origin main` — 항상 최신 `main`에서 시작한다.

## Phase 1: 문제 분석 & 해결책 제시

> **단순 변경 스킵**: 사용자가 구체적인 변경 내용을 직접 명시한 경우 Phase 1을 스킵하고 단일 작업으로
> 구성해 Phase 1.5로 직행한다.

1. 제시된 증상·에러·재현 질문을 분석한다. **최종 답변만 보고 원인을 단정하지 않는다** — `/ask` 응답의
   `trace`(노드별 판정)와 `policy_version`(실행된 검색 정책)을 확보하고, 서버를 거친 문제면 BE 로그를
   사용자에게 요청한다.
2. 관련 코드를 탐색해 원인을 파악한다. 계약의 형태는 문서가 아니라 `app/api/routes.py`의 요청·응답
   모델에서, 검색 정책은 `app/agent/graph.py`의 `PRESETS`에서 확인한다.
3. 해결책을 번호와 함께 제시한다. 하나의 해결책 안에 동작 변경과 표층 변경이 섞일 수 있으므로
   **해결책 내부를 작업(task) 단위로 분리**한다.

   ```
   해결책 N: [한 줄 요약]
   ├─ 작업 N-a [동작]    변경 내용    | 영향 파일: app/agent/nodes/answerer.py
   ├─ 작업 N-b [비동작]  변경 내용    | 영향 파일: docs/architecture.md
   └─ 작업 N-c [동작]    변경 내용    | 영향 파일: ...
   위험도: 낮음 / 중간 / 높음
   ```

   작업 분류 기준 — **"이 변경이 옳게 됐는지를 테스트가 단언할 수 있는가"** 하나로 가른다:
   - `[동작]`: 라우팅·게이트 판정, 노드 입출력, 검색·융합·리랭크 결과, API 응답, 채점·집계 로직처럼
     관측 가능한 동작이 바뀐다 → Test-First 절차 (`automation/freeze.md`)
   - `[비동작]`: 단언해봐야 값을 복붙하는 토톨로지가 되는 것. 로그 문구, 주석·문서·설정,
     `scripts/**`·`.github/**`·`automation/**` → 일반 코드 변경 절차

   **영향 파일 목록은 Phase 1.5의 입력이므로 빠짐없이 적는다.**

4. **사용자 확인 대기** — 적용할 해결책 번호 선택 요청 (예: "1, 3번 적용")

## Phase 1.5: 라우팅 판정 (기계 검사)

선택된 해결책의 **영향 파일 전체**를 아래 게이트에 대조한다. 사람의 해석이 아니라 경로 매칭이다.

| 게이트 | 경로 패턴 | 걸리면 |
|---|---|---|
| **계약** | `app/api/**` | **스펙 승격** |
| **검색·생성 정책** | `app/agent/graph.py`, `app/config.py`, `app/llm/prompts.py`, `app/retrieval/**` | **스펙 승격** |
| **새 모듈** | `app/<기존에 없던 디렉토리>/`, `app/agent/nodes/<기존에 없던 파일>` | **스펙 승격** |

**하나라도 걸리면 이 절차를 중단**하고 아래 「승격 핸드오프」를 산출한다. 중단 시점에는 아직 브랜치를
만들지 않았으므로(Phase 3 이전) 정리할 잔재가 없다. 걸리지 않으면 Phase 2로 진행한다.

> **이 표는 하네스 이식 시점(2026-09-11)의 초기값이다.** 첫 스펙이 이 레포의 계약과 모듈 경계를
> 확정하면 그에 맞춰 고친다. BE판의 「보안」 게이트는 옮기지 않았다 — 이 레포에는 인증·보안 계층이
> 없다. 생기면 추가한다.

**검색·생성 정책 게이트가 이 레포에서 넓은 이유**: 그 파일들의 값(게이트 컷·top_k·리랭크 발췌·RRF K·
프롬프트)은 BE 운영값과 `docs/experiments/`의 실측에 묶여 있다. 점수 컷은 기권과 생성 비용을 함께
옮기고, 프롬프트 한 줄의 효과조차 반복 실험으로 재야 했다(`docs/experiments/2026-08-23-facet-prompt.md`).
값을 옮기는 변경은 「6개월 뒤 누군가 근거를 찾을」 결정이다.

- **오탐은 안전한 방향이다**: 정책 파일을 건드렸지만 주석 수정이라 동작이 그대로인 경우, 스펙을 한 번
  더 쓰는 비용이 발생할 뿐이다.
- **통과**했으면 판정 결과를 사용자에게 **한 줄로 보고**한 뒤 Phase 2로 진행한다. **걸렸으면** 한 줄
  보고로 끝내지 않고 「승격 핸드오프」 블록까지 내놓는다 — 진단을 여기까지 한 세션이 그 내용을 넘기지
  않으면, 받는 쪽이 처음부터 다시 조사한다.

## 승격 핸드오프

Phase 1.5와 Phase 4의 게이트가 걸렸을 때 **양쪽이 같은 형식으로** 내놓는 산출물이다. 이 절차의 마지막
행위이며, 이후는 BE 레포의 몫이다.

**이 하네스는 BE 레포에 쓰지 않는다.** 레포 경계를 넘는 쓰기를 하네스가 자동으로 하지 않는다 —
산출물은 **사용자가 BE 세션에 그대로 붙여넣는 텍스트**이고, 거기서 `/spec`이 받는다.

### 산출 형식

````
/spec <한 줄 범위>

## 증상
관측된 것과 재현 경로(질문·프리셋·policy_version·trace 발췌).

## AGENT 진단 결과
원인과 그렇게 판단한 근거를 `파일:라인`으로 짚는다.

## AGENT에서 끝낼 수 없는 이유
걸린 게이트(계약 / 검색·생성 정책 / 새 모듈)와 그 판정 근거.

## 현재 형태
계약이면 `app/api/routes.py`의 요청·응답 모델, 정책이면 해당 프리셋의 `AgentConfig` 값과
policy_version 문자열의 지금 모습. 없는 필드·엔드포인트를 요구하는 문제면 「없다」는 사실 자체를 적는다.

## 범위 분할 제안 (BE) / (FE) / (AGENT)
레포마다 책임질 부분의 예상 경계.

## AGENT 쪽 영향 파일
Phase 1에서 수집한 목록.
````

각 절을 두는 이유:

- **`/spec`은 실측 조사를 자기가 한다.** 「현재 형태」와 「AGENT 쪽 영향 파일」은 그 조사에서 이 레포
  몫을 덜어주는 입력이지, 조사를 대신하는 것이 아니다 — 넘긴 값이 스펙에 그대로 실릴 거라고 기대하지 않는다.
- **「범위 분할 제안」이 이 블록에서 가장 값나가는 줄이다.** `/implement` Phase 0은 **`(AGENT)` 라벨이
  없으면 사람에게 되묻고 멈춘다.** 진단을 마친 이 세션이 경계를 가장 잘 아는 시점이므로 여기서
  제안한다 — **확정이 아니라 제안이다.** 확정은 `/spec`이 조사 후에 한다.
- **「AGENT에서 끝낼 수 없는 이유」를 빼지 않는다.** 이게 없으면 받는 쪽은 왜 여기서 직접 안 고치고
  넘겼는지 몰라, 게이트가 이미 배제한 국소 수정을 다시 검토한다.

### 산출 뒤

1. 블록을 사용자에게 전달하고 **BE 세션에서 `/spec`으로 이어가야 함을 명시**한다. `/spec`은
   `disable-model-invocation: true`라 사람이 직접 불러야 한다.
2. 스펙이 BE `dev`에 착지하면 그 번호로 **`/implement <번호>`가 새로 시작한다.** 이 절차가 이어받지
   않는다 — 승격은 여기서 끝이다.

## Phase 2: 의존성 분석 & 실행 계획

1. 선택된 해결책의 모든 작업을 평탄화해 목록을 만든다.
2. 작업 간 의존성을 분석한다:
   - **같은 파일 수정** → 순차
   - **같은 모듈의 연관 로직 변경** → 순차
   - **서로 다른 모듈·파일을 독립 변경** → 병렬 가능
3. 실행 계획을 보고한다 (병렬 그룹 A/B, 순차 그룹 C 형태로 그룹핑, 각 작업의 타입과 절차 명시).
4. 보고 후 **사용자 확인 없이** 즉시 Phase 3으로 진행한다.

## Phase 3: 브랜치 (이슈 생성 없음)

코드 변경 **전에** 브랜치를 만든다 — 병렬 워크트리의 base가 필요하기 때문이다.

1. 변경 성격에 맞는 타입을 고른다 (`automation/ship.md` Phase 1의 타입 테이블이 원천).
   **이 하네스의 기본값은 `[BUG]`(`bug/`)다** — 운영에서 관측된 문제로 진입하는 경로이기 때문이다.
   머지 전에 자체 발견한 것을 여기로 가져왔다면 `[FIX]`(`fix/`)로 고른다. 이 구분은 표본을 세기
   위한 것이므로 편의로 뭉개지 않는다.
2. 브랜치 `<prefix>/<슬러그>` 생성 → checkout. 슬러그는 짧은 **영문 kebab-case**.
3. **이슈를 만들지 않는다** (`automation/ship.md` 「워크플로우 전제」 — 이 레포는 PR-퍼스트다).

   > **커밋 제목에 `#`를 쓰지 않는다.** 이슈가 없어 `#N`에 넣을 번호가 없고, 임의의 번호를 `#`와 함께
   > 쓰면 GitHub이 같은 번호의 PR·이슈로 자동 링크한다. squash 머지가 붙이는 `(#PR번호)`가 추적 식별자다.

4. **Preflight 이월 변경 처리**: Preflight 3에서 **관련 있음**으로 확인된 stash만 여기서 복원한다:
   `git stash pop` → `git add -A && (git diff --cached --quiet || git commit -m "wip: preflight carry-over")`
   - 이는 병렬 통합(cherry-pick)의 전제조건이다. 더티 워킹 트리 위에서 cherry-pick하면
     `error: your local changes would be overwritten`으로 실패하고, 병렬 워크트리에는 이 변경이 없어
     의미적 충돌이 통합 시점까지 감지되지 않는다.
   - 충돌 시 자체 해결한 뒤 진행하고, 해결 내역을 사용자에게 보고한다.
   - **무관함**으로 분류된 stash는 손대지 않는다 — Phase 6까지 stash에 남는다.
   - 이 WIP 커밋을 따로 정리할 필요는 없다. `automation/pipeline.md`가 **squash 머지**를 쓰므로
     브랜치의 커밋들은 머지 시점에 하나로 합쳐진다.

> **중단 시 정리**: Phase 3부터는 브랜치가 존재하므로, 이후 단계가 실패하거나 사용자가 중단하면
> 브랜치 삭제 여부를 확인한다. 이슈가 없으므로 닫을 것은 없다.

## Phase 4: 코드 변경

### 사전 단계: 테스트 동결 (`[동작]` 작업 대상)

`automation/freeze.md`를 읽고 아래 파라미터로 실행한다. **`[동작]` 작업이 없으면 이 단계 전체를 스킵**한다.

| 파라미터 | 값 |
|---|---|
| 명세 | Phase 1에서 확정된 해당 작업의 변경 내용 + `docs/architecture.md`의 관련 § |
| 작업 ID | **브랜치 슬러그** (이슈 번호가 없다) |
| 동결 단위 | `[동작]` 작업 1개 = 1 단위 (전 단위 완료 후 커밋·목록 기록 1회) |
| 참조 패턴 파일 | `tests/conftest.py` + 대상 모듈의 기존 `tests/test_*.py` 1~2개 전문 |

커밋 제목은 **`[TEST] <슬러그> <요약> 수용 기준 테스트 동결 (작성: Codex)`**를 쓴다. `#` 금지 규칙은
그대로 승계한다. 동결은 **구현(병렬/순차) 시작 전에 완료**한다.

### 실행 모드

- **그룹 2개 이상** → 각 그룹을 에이전트로 병렬 실행. 통합 완료 전까지 메인 세션은 코드를 직접
  수정하지 않고 **cherry-pick 통합만** 담당한다.
- **그룹 1개** → 워크트리 없이 메인 세션에서 순차 실행.

### 병렬 실행

- **base**: 각 워크트리는 반드시 **현재 브랜치의 HEAD**에서 생성한다. 동결 커밋·WIP 커밋이 HEAD에
  포함돼야 재현이 가능하다.
- **네이밍**: 워크트리 내 임시 브랜치 `wt/<슬러그>-<그룹>`(예: `wt/rerank-fallback-A`).
- **에이전트 프롬프트에 포함할 것**: 그룹의 작업 상세, 타입별 절차 전문, 그룹 내부 순서,
  **커밋 소유권**(작업마다 워크트리 내 로컬 커밋 + 완료 보고에 **커밋 SHA 목록 순서대로 필수** —
  메인 세션이 cherry-pick 대상을 수집하는 유일한 경로), push·PR 금지.
- **인터프리터와 import 대상**: 워크트리에는 `.venv`가 없다. 본 트리의 `.venv/bin/python`을 쓰되,
  그 venv는 본 트리를 에디터블로 설치해 두었으므로 **워크트리 루트에서 실행해 워크트리의 `app`이
  import되는지** 먼저 확인한다(`python -c 'import app; print(app.__file__)'`). 본 트리가 잡히면 남의
  코드를 검증하고 조용히 통과한다.
- **e2e는 병렬 에이전트에게 시키지 않는다.** 병렬 에이전트는 구현 + `make lint && make typecheck && make test`
  까지만 수행하고, e2e는 통합 후 메인 세션이 일괄 수행한다(Phase 5) — e2e가 DB 같은 공유 자원을 쓰게
  되면 워크트리끼리 경합한다.
- **동결 목록**: `.cure-implement/`는 git-ignored라 워크트리 체크아웃에 딸려 가지 않는다. 훅은
  `$CLAUDE_PROJECT_DIR`의 목록을 읽고 대상 파일을 그 파일이 속한 워크트리 루트 기준 상대 경로로
  비교하므로, 목록이 세션 프로젝트 디렉토리에 있으면 워크트리 편집에도 매칭된다. 어느 경우든 사후
  감사가 최종 방어선이다.
- **통합**: 모든 에이전트 완료 후 보고된 SHA를 **그룹 알파벳 순(A→B→C)**, 그룹 내부는 보고 순서로
  cherry-pick한다 (독립 그룹이라 이론상 순서 무관하지만 충돌 해결의 재현성을 위해 고정).
  통합 직후 `make typecheck && make test`로 통합 검증하고, 각 워크트리를 `git worktree remove` +
  임시 브랜치 삭제한다.

### `[동작]` Test-First 구현 절차

1. 동결된 테스트·fixture를 읽고 기대하는 인터페이스와 동작을 파악한다
2. 명세 + 동결 테스트를 참조해 스텁 본문을 구현한다. 구현 중 새 시그니처가 필요해지면 테스트에
   맞춰 임의 생성하지 않는다 — 작업 명세와 스텁을 먼저 갱신하고 재파생·재동결한 뒤 재개한다
3. 테스트 실행 → 실패 시 **구현을 수정**해 재실행 (테스트는 동결 상태라 수정 불가)
4. 이의 제기는 `automation/freeze.md`의 「이의 제기(TEST-DISPUTE)」를 따른다
5. `make typecheck && make test`

### `[비동작]` 일반 절차

1. 변경 적용 → `make lint && make typecheck`
2. **기존 테스트 영향 검증**: 변경 대상을 의존하는 기존 테스트를 실행한다. 실패하면 테스트를
   수정하되, **동결된 테스트에 영향이 가면 수정하지 말고** TEST-DISPUTE에 준해 보고한다 (훅이
   Edit/Write를 차단하므로 어차피 직접 수정 불가). 영향받는 테스트가 없으면 스킵.
3. 변경 파일 재검토: 타입 오류, import 누락, 노드↔오케스트레이터 경계(`docs/architecture.md` §2) 준수

### 계약 이탈 감지 (모든 작업 공통)

구현 중 **Phase 1.5의 게이트에 해당하는 변경이 필요해지면 그 자리에서 중단**하고 사용자에게 보고한다.
임의로 진행하지 않는다 — 진단 단계에서 보이지 않던 계약·정책 변경이 구현 중 드러난 것이므로,
승격 여부를 사람이 결정해야 한다.

> 이는 동결 테스트를 고치고 싶어질 때 TEST-DISPUTE로 멈추는 것과 같은 원리다 — **하네스는 스스로
> 경계를 넘지 않는다.**

**승격을 택하면 브랜치를 버린다.** Phase 1.5와 달리 여기서는 브랜치·동결 커밋·부분 구현이 이미
존재하는데, 그것을 들고 갈 곳이 없다:

- `/implement` Phase 0은 `git status` clean 확인 → `main` checkout → **새 브랜치 생성**이다.
  남겨 둔 브랜치를 이어받는 경로가 애초에 없다.
- 부분 구현이 남아 있으면 `/implement` Phase 2의 「구현이 이미 존재하면 중단하고 보고한다」 가드에
  **하네스 우회 신호로 오탐**된다. 그 가드는 되돌리는 절차를 일부러 두지 않는다.
- 동결 테스트는 **미확정 명세에서 파생된 심판**이다. 스펙이 확정되면 `/implement` Phase 2가 그
  스펙으로 다시 파생한다 — 여기서 만든 것을 물려주면 잘못된 기준을 확정된 것처럼 넘기는 셈이다.

**버리는 것은 브랜치이지 알아낸 것이 아니다.** 순서를 지킨다:

1. 「승격 핸드오프」 블록을 먼저 산출한다 — 브랜치를 지우기 전에 진단 결과를 건져낸다.
2. `automation/freeze.md`의 「동결 해제」를 수행한다. 그 규칙은 「머지 성공 후에만」이지만
   **폐기에 의한 해제가 그 유일한 예외**다 — 해제하지 않으면 훅이 남은 목록으로 이후 세션의 Edit까지
   계속 막는다.
3. `git checkout main` → `git branch -D "<브랜치명>"`. push한 적이 있으면 원격 브랜치도 지운다.
4. 사용자에게 블록과 함께 **브랜치를 버렸다는 사실**을 보고한다.

## Phase 5: 통합 & 검토

1. 전체 변경사항 보고: 작업별 변경 파일, 테스트 결과 요약
2. **최종 검증** — `automation/ship.md` Phase 2와 **같은 순서**로 돈다:

   ```
   make lint
   make typecheck
   make test
   make test-e2e
   ```

   - **e2e를 여기서 도는 이유는 병렬 실행이 그것을 미루도록 설계돼 있기 때문이다.** Phase 4는 병렬
     에이전트에게 e2e를 금지한다. 구조적으로 미룬 대가를 갚는 자리가 여기이고, **통합된 트리에서
     e2e를 처음 밟는 지점**이 이 단계다.
   - e2e는 CI `test-e2e` 잡으로도 돈다(컨테이너 테스트 — Docker가 있어야 한다). 그래도 여기서 먼저
     도는 이유는 위와 같다 — CI는 push 뒤에야 돌고, 통합된 트리의 e2e 실패는 여기서 고친다.
   - `automation/bin/`을 고쳤으면 `automation/bin/smoke-test.sh`도 돈다 — 이것은 CI 잡이 아니다.
   - **테스트 실패는 이 시점의 정상 경로다**: 병렬 에이전트는 통합된 트리를 본 적이 없다. 실패 시
     사용자에게 떠넘기고 멈추지 않는다 — **동결을 유지한 채 구현만 수정**하고 재실행하는 루프를
     GREEN까지 반복한다.
   - **루프 내 재실행은 실패분만 대상**으로 한다. 전부 GREEN이 된 뒤 최종 확인으로 전 구간 1회 재실행.
   - **서킷 브레이커**: 동일 테스트가 **3회 연속** 실패하면 루프를 멈추고 현황(실패 테스트, 시도한
     수정, 원인 분석)을 보고한 뒤 지시를 대기한다.
3. **동결 무결성 사후 감사**: 동결이 있었으면 `automation/freeze.md`의 「사후 감사」를 실행한다.
   감사는 항상 마지막 코드 변경 뒤에 오며, 이후 코드가 다시 바뀌면 재실행한다.
4. **사용자 확인 대기** — 추가 수정 요청 시 반복. OK 시에도 **동결은 아직 해제하지 않는다**
   (머지 실패로 재수정하는 시나리오에서 테스트가 무방비가 되지 않도록).

   > **이 확인을 생략하지 않는다.** Phase 6이 `automation/ship.md`에 위임하면 ship Preflight가 feature
   > 브랜치를 감지해 **Phase 1·3을 스킵**하므로 ship이 가진 사용자 확인이 건너뛰어지고, 이후
   > `automation/pipeline.md`가 PR → 게이트 → **squash 머지**까지 멈추지 않는다.

## Phase 6: PR·머지

`automation/ship.md`를 읽고 실행한다. 현재 feature 브랜치에 있으므로 ship의 Preflight가 이를 감지해
**Phase 1·3을 스킵하고 Phase 2(검증)로 직행**한다.

전달할 컨텍스트: 브랜치명, 타입, Phase 5의 변경사항 요약, 그리고 **Phase 5-2 검증 완료 사실**
(전 구간 green 여부).

**머지 성공 후**:
1. `automation/freeze.md`의 「동결 해제」를 수행한다.
2. Preflight에서 **무관함**으로 분류해 stash에 남겨둔 이월 변경이 있으면 `git stash pop`으로 복원하고,
   복원 사실을 보고한다. 머지가 실패해 재수정하는 동안은 stash를 그대로 둔다.
3. 서버 반영은 이 절차의 범위가 아니다 — cure-agent-be가 맡는다. 최종 보고에 그 사실을 적는다.

## 규칙

- 해결책 제시 시 코드 변경 없이 분석만 수행한다
- 사용자가 선택하지 않은 해결책은 절대 적용하지 않는다
- **승격 판정 시 브랜치를 남기지 않는다** — 「승격 핸드오프」로 진단 결과만 넘기고, 브랜치·동결·
  부분 구현은 폐기한다. BE 레포에는 이 하네스가 직접 쓰지 않는다
- 하나의 해결책 안에서도 `[동작]`/`[비동작]` 작업을 반드시 분리해 제시한다
- `[동작]` 테스트 실패 시 구현을 수정한다 — **기본 추정은 구현 결함, 입증 책임은 구현 쪽**
- 노드는 `app/agent/state.py`의 타입으로만 말하고, 배선은 `app/agent/graph.py`만 한다 (§2)
- 검색 정책 값의 단일 출처는 `AgentConfig`/`PRESETS`다 — `Settings`에 사본을 두지 않는다 (§2)
- 테스트는 LLM·임베딩 API를 실제로 부르지 않는다 — Protocol 뒤의 가짜를 꽂는다 (§4)
- `docs/experiments/`의 기존 관측 숫자를 고치지 않는다 (§5)
- **커밋 제목에 `#`를 쓰지 않는다** (Phase 3의 자동 링크 오작동)
- 상태 파일은 `.cure-implement/`(git-ignored)를 `/implement`와 공유한다
- 모든 `gh`/`git` 명령 실패 시 에러 내용을 사용자에게 보고한다
