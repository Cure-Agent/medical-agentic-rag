# freeze — 수용 기준 테스트 동결 (하네스 중립 명세)

구현 전에 수용 기준 테스트를 **독립 작성자로 파생**하고, 기계 검증을 통과시킨 뒤 **동결**한다.
동결된 테스트는 구현 루프 중 수정할 수 없으며, 위반은 사후 감사로 탐지된다.

> **이 파일은 하네스 중립 「진실의 원천」이다.** 직접 실행 대상이 아니라, 동결이 필요한 상위 절차가 호출한다:
> - `/implement` (`.claude/commands/implement.md` Phase 2·4) — 명세 출처는 **BE 레포의**
>   `docs/specs/<번호>`이며 `scripts/fetch_spec.py`가 조달한다.
> - `/problem` (`automation/problem.md` Phase 4) — 명세 출처는 그 절차의 Phase 1에서 확정된
>   **해결책의 작업 명세**다.
>
> 두 호출자의 차이는 **명세가 어디서 오는가**뿐이다. 아래 절차는 양쪽에서 동일하다.
> 원칙의 원본은 cure-agent-be `docs/sdd.ko.md` 「동결은 어떻게 강제되는가」다.

## 원칙

**심판(테스트)과 선수(구현)를 같은 에이전트가 만들지 않는다.** 같은 에이전트가 둘 다 만들면
스펙 오독이 테스트와 구현 양쪽에 복제되어 서로를 통과시킨다. 테스트는 Codex가 명세에서 독립
파생하고, 구현 하네스는 **스텁 준비·리뷰·동결**만 담당한다 — assertion을 직접 수정하지 않는다.

Codex를 쓸 수 없으면 구현 하네스 단독 폴백으로 진행하되, **동결 이하의 절차는 모드와 무관하게
동일하다** — 동결의 가치 절반(구현 루프 중 테스트 변조 방지)은 작성자 분리 없이도 성립한다.

## 호출 파라미터

상위 절차가 아래를 확정한 뒤 이 문서의 절차에 진입한다.

| 파라미터 | `/implement` (스펙 경로) | `/problem` (운영 문제 경로) |
|---|---|---|
| **명세** | BE 레포 `docs/specs/<번호>`의 **(AGENT) 수용 기준** + 이 레포 `docs/architecture.md` §링크 | Phase 1에서 확정된 **해결책의 작업 명세** + `docs/architecture.md` 관련 § |
| **작업 ID** | **스펙 번호** (예: `41`) | **브랜치 슬러그** (예: `rerank-fallback`) — 이슈 번호가 없다 |
| **동결 단위** | 스펙 1개 = 1 단위 | `[동작]` 작업 1개 = 1 단위 (N개 가능) |
| **참조 패턴 파일** | `tests/conftest.py`(가짜 Retriever·근거 팩토리) + 대상 모듈의 기존 `tests/test_*.py` 1~2개 전문 | (동일) |

**동결 단위가 여러 개면 1~5번을 단위마다 반복**하고, 6~7번(커밋·목록·SHA)은 전 단위 완료 후 **1회**
수행한다. 선택된 작업이 전부 `[비동작]`이어서 동결 단위가 0개이면 이 절차 전체를 스킵한다.

**커밋 제목에 `#`를 쓰지 않는다.** 이 레포는 이슈를 만들지 않으므로(`automation/ship.md`
「워크플로우 전제」) `#N`에 넣을 이슈 번호가 없고, spec 번호를 `#`와 함께 쓰면 **GitHub이 같은
번호의 PR·이슈로 자동 링크한다** — BE(spec 18 구현이 이슈 #18 「배포」에 연결)와 FE(`[TEST/#09]`
등이 무관한 PR에 연결) 양쪽에 전례가 있다. 형식은 **`[TEST] spec <번호> <요약>`**이며, squash 머지가
붙이는 `(#PR번호)`가 추적 식별자다.

> 아래 절차 본문의 `spec <번호>`는 **작업 ID 표기의 자리표시자**다 — `/problem` 경로에서는
> `<슬러그>`로 읽는다(예: `[TEST] rerank-fallback 수용 기준 테스트 동결`). `#` 금지는 양쪽 공통이다.

상태 파일은 호출자와 무관하게 `.cure-implement/`(git-ignored)를 공유한다 — PreToolUse 훅
(`.claude/hooks/freeze-test-files.sh`, `.claude/settings.json`에 등록)이 이 경로를 참조하므로
하네스별로 나누지 않는다.

아래 명령의 `<PY>`는 Makefile의 `PY`와 같은 인터프리터다(로컬 `.venv/bin/python`).

## 절차

1. **스텁 준비(구현 하네스)**: import·타입 검사에 필요한 최소 시그니처(노드 팩토리·Protocol·Pydantic
   모델 뼈대·라우트 배선)와 fixture 컨벤션만 만든다. **로직 금지** — 본문은 `raise NotImplementedError`
   같은 무동작으로 둔다. 인터페이스 시그니처는 아키텍처 결정이므로 구현측이 소유한다 — 테스트
   작성자에게 맡기면 코드베이스 컨텍스트가 가장 적은 에이전트에게 설계권이 넘어간다.
   스텁은 **동결 커밋과 분리해 먼저 커밋**한다(`[TEST] spec <번호> 스텁 준비`) — 동결 커밋에
   테스트·fixture만 남아야 감사가 파일 목록을 동결 커밋 자체에서 복원할 수 있다.
   커밋 직후 `git rev-parse HEAD > .cure-implement/stub-commit.txt` — 「디스퓨트 후 재검증」의
   **RED 기준선**이다. 동결 커밋의 부모로 추정하지 않고 그때그때 기록한다: 스텁 커밋과 동결 커밋
   사이에 기계적 수정 커밋이 끼면 추정이 틀어진다.

   > **이 절차는 구현이 아직 없다고 전제한다.** 스텁을 만들려는데 **구현이 이미 있으면 중단하고
   > 보고한다.** 그 상태는 이 하네스를 지나서는 나올 수 없다 — `/implement`는 Phase 2 다음이
   > Phase 3이다. 즉 하네스를 우회했다는 신호이고, **되돌리는 절차를 여기 두지 않는다**: 복구 경로를
   > 적어두면 우회가 지원되는 모드로 굳는다. 어떻게 그 상태가 됐는지를 먼저 밝히는 것이 순서다.

2. **테스트 명세 프롬프트(구현 하네스)**: `.cure-implement/<작업 ID>-test-prompt.md`에 작성 —
   명세 전문, 수용 기준별 검증 포인트, **참조 패턴 파일 전문**(경로가 아니라 내용 — 아래 「참조 파일은
   인라인한다」 참조), 스텁 시그니처, 출력 파일 경로, 그리고 다음 필수 문구:
   - **"테스트·fixture 외 파일 수정 금지"**
   - **"모든 테스트는 스텁 상태에서 실패해야 한다"** (이미 통과하는 테스트는 구현을 검증하지 못하는 공허 테스트)
   - **"어떤 셸 명령도 실행하지 말고 파일 작성만 하라"** — 수집·타입 검사·RED 검증은 전부 호출측
     (5번 게이트)이 수행한다. codex가 검증 프로세스(pytest·pyright 등)를 띄우면 실행 시간이 폭증하고
     프로세스 트리가 호출 경계를 넘어 살아남아, **강제 종료 후에도 파일이 뒤늦게 착지해 동결 무결성을
     오염**시킨다 (BE 9단계 실증)
   - **"LLM·임베딩 API를 실제로 부르지 말고 가짜를 꽂아라"** — 외부 유료 경계는 `Retriever`·`Reranker`
     Protocol과 LLM 대역으로 치환한다(`docs/architecture.md` §4). 실키로 도는 테스트는 CI에서 조용히
     깨지거나 과금한다

   **참조 파일은 인라인한다 — 경로만 주면 안 된다.** 셸 금지 문구 때문에, codex 세션에 비셸 파일
   조회 수단이 없으면 경로로 지목한 파일을 **읽을 방법이 원천적으로 없다.** 두 요구가 충돌하며,
   막히는 쪽은 언제나 참조다. BE `cure-agent-be#106` 1차 파생이 정확히 여기서 멈춰 e2e를 내지
   못했다("필수 참조 파일을 읽을 비셸 파일 조회 도구가 현재 세션에 없습니다"). **그때 codex가
   추측으로 골격을 지어내지 않고 보고한 것은 올바른 동작이다** — 반려 사유가 아니라 프롬프트 결함 신호다.
   - e2e처럼 골격 복제가 필요하면 셋업·헬퍼·유사 단언 블록까지 수백 행이어도 전부 싣는다.
     `cure-agent-be#106` 2차는 참조 5개 약 960행을 인라인해 통과했다.
   - 프롬프트가 길어지는 비용은 **심판을 눈감고 쓰게 하는 것보다 싸다.** 참조 없이 짜인 테스트는
     없는 시그니처를 지어내거나(`cure-agent-be#102` 1차 실증) 수집 단계에서 죽어, 정작 검증 대상에
     닿지 못한다.
   - 인라인 범위 판단이 애매하면 **넓게 잡는다.** 부족하면 왕복 한 번이 통째로 낭비되지만, 넘치면
     토큰만 더 쓴다.

   **복합 기준은 동작 단위로 쪼개 넘긴다.** 수용 기준 한 항목에 동작이 둘 이상이면(「A하고 B한다」,
   「A로 두되 B에 기록한다」) 프롬프트에서 **각 동작을 별도 검증 포인트로 나열**하고 각각 단언하게
   요구한다. 한 항목으로 넘기면 codex는 대개 **앞의 동작만** 단언하고, 뒤는 아무 테스트도 보지 않아
   무방비가 된다.
   - 실증(BE): spec 23 기준 8은 ⑴ 등급 문자가 인식되면 미상 근거수준이어도 성공으로 본다 ⑵ 원문
     표기를 진단에 모아 보고한다 — 였다. 파생된 테스트는 ⑴만 단언했고, ⑵는 구현이 누락된 채 동결
     게이트·전 구간 검증·CI를 전부 통과해 **프로덕션까지 갔다**(`cure-agent-be#120`에서 개정·구현).
   - 동결은 「**테스트가 명세를 대표한다**」는 전제 위에 선다. 한 기준의 일부만 단언되면 그 전제가
     깨지므로, 쪼개는 것은 취향이 아니라 전제를 지키는 일이다.
   - 명세 자체가 복합이면 **쪼갤 수 있는지 먼저 보라** — 쪼개기 어려운 기준은 대개 두 결정을 한
     문장에 눌러 담은 것이고, 그 자체가 명세 결함 신호다.

3. **Codex 호출(구현 하네스)** — 4중 방어 + 자연 종료:
   ```bash
   # timeout은 있을 때만 상한 래핑. macOS 기본엔 timeout/gtimeout이 없으므로 없으면 그냥 실행 —
   # 최종 backstop은 하네스의 명령 실행 timeout이다. perl alarm 등 강제 kill 금지.
   TO=""; command -v timeout >/dev/null && TO="timeout 480"; command -v gtimeout >/dev/null && TO="gtimeout 480"
   $TO codex exec --sandbox workspace-write -C <이 레포 절대경로> \
     --ephemeral \
     -m gpt-6-astra \
     -c model_reasoning_effort="medium" \
     -c mcp_servers='{}' \
     --color never \
     < .cure-implement/<작업 ID>-test-prompt.md \
     > .cure-implement/<작업 ID>-codex.log 2>&1
   ```
   - 프롬프트는 반드시 **stdin 리다이렉트(`< file`)** — positional 인자로 주면 stdin 대기 hang
   - 출력은 **파일 리다이렉트** — 파이프 상속 hang 방지. codex 출력에 파이프(`| tail` 등) 금지
   - **강제 kill(perl alarm·SIGALRM) 금지** — codex는 "파일만 쓰는 작업"이라 2번 문구가 지켜지면
     자연 종료한다. 조기 사살은 orphan 작업의 **지연 파일 착지**를 만들어 이후 커밋·동결을 오염시킨다.
     오래 걸리면 백그라운드로 돌려 세션을 묶지 않고 완료 통지 후 점검한다
   - **완료 판정은 exit code가 아니라 산출물로**: 로그 말미의 완료 응답(파일 목록·tokens used)과
     출력 파일 존재를 확인한다. timeout으로 끊겼어도 "파일은 이미 디스크에 있을 수 있다" — 실패로
     판정하기 전에 반드시 파일을 점검하고, **재시도 전 `pgrep -fl "codex exec"`로 잔존 프로세스를
     확인**한다(살아 있으면 완료를 기다린다 — 죽이거나 병행 재시도하지 않는다)
   - **모델·effort 모두 플래그로 명시 고정(`gpt-6-astra`/`medium`)** — config 편차로 심판 품질이
     조용히 열화되는 것을 막는다. 심판은 구현 루프 전체가 딛고 설 기준이므로 여기서 아끼지 않는다.
     사고 단계가 수 분 이상 길어질 수 있으나, 위의 "파일만 작성·자연 종료·산출물 기준 판정"
     전제에서 이는 hang이 아니라 정상 대기다. **핀 모델 미가용**(model not found류) 시 기본
     모델(`-m`·effort 제거)로 1회 재시도하고 동결 커밋에 사용 모델을 명시한다
   - 실패 시 1회 재시도 → 그래도 실패면 **구현 하네스 단독 폴백** — **동결 포함 절차 동일**,
     동결 커밋에 `작성: Claude 단독` 명시. 이때 자기 리뷰는 독립성이 없으므로 5번 기계 게이트가 주
     방어선이 된다. **폴백 착수 전 잔존 codex 프로세스가 없음을 확인**한다 — 뒤늦은 착지와 폴백
     산출물이 경합하면 동결 대상이 오염된다

4. **리뷰(구현 하네스)** — 구현자 관점 개입 금지, 다음만 검사:
   - ① 수용 기준 전 항목이 커버되는가 — **항목 수가 아니라 동작 수로 센다.** 한 기준에 동작이
     둘이면 단언도 둘이어야 한다(2번 「복합 기준은 동작 단위로 쪼개 넘긴다」). 기준 목록과 테스트
     이름을 나란히 놓고 세면 개수는 맞는데 **뒤쪽 동작이 비어 있는** 경우를 놓친다
   - ② **공허 통과** 가능성(스텁의 예외를 삼키는 단언, 가짜가 정답을 그대로 돌려주는 구성 등)이 있는가
   - ③ 명세에 없는 가정을 추가했는가
   - ④ `git status`로 테스트·fixture 외 파일 무변경 확인
   - 문제 발견 시 프롬프트를 보강해 **Codex에 재작성 요청** — 구현 하네스가 assertion을 직접 고치지
     않는다. import 오류 등 기계적 수정만 허용하며 커밋 메시지에 기록한다.

5. **동결 게이트 — 3계층 기계 검증(구현 하네스)**. 4번 리뷰는 정성 검사라 커버리지·가정을 보고,
   이 게이트는 기계 검사다 — 둘은 보완재. 세 계층 모두 통과해야 동결한다:
   - ① **Discovery**: `<PY> -m pytest --collect-only -q <신규 테스트 경로>` 출력에 신규 테스트가
     실제로 잡히는지 확인한다 — 수집 0건(종료코드 5)은 러너 패턴(`test_*.py` 파일·`test_*` 함수·
     `Test*` 클래스) 불일치로, 영원히 조용히 통과(스킵)되는 파일이라는 뜻이다. e2e는 `tests/e2e/`
     아래에 있어야 `make test-e2e`가 잡고, 그 밖의 파일은 `make test`가 잡는다
   - ② **빌드 GREEN**: `make typecheck` 통과 — 동결 커밋은 이후 구현의 base이므로 타입 검사를
     통과하는 커밋이어야 한다. 이 레포에는 컴파일 단계가 없어 pyright가 이 계층을 맡는다
   - ③ **실행 RED (테스트 단위)**: **모든 테스트가 개별적으로** 실패하는지 확인한다. 스위트 단위의
     "전부/대부분 실패"로 만족하지 않는다 — `<PY> -m pytest <신규 테스트 경로> -rA`로 스텁 상태에서
     **통과(PASSED)하는 테스트를 기계적으로 열거**하고, 건별로 정당화되지 않으면 Codex에 재작성
     요청한다. 스텁(= 아무것도 안 하는 구현)을 죽이지 못하는 테스트는 정의상 공허 테스트다. 특히
     `pytest.raises(Exception)`처럼 스텁의 `NotImplementedError`까지 삼키는 단언(리뷰 ②의 함정)이
     여기서 기계적으로 걸린다. 수집 에러(import 실패)로 죽으면 RED가 아니라 broken — 수정 후 재검증한다

6. **동결 커밋**: `[TEST] spec <번호> <요약> 수용 기준 테스트 동결 (작성: Codex)` — 폴백 시
   `작성: Claude 단독`, 기계적 수정·모델 폴백이 있었으면 사유 병기. **동결 커밋에는 테스트·fixture만
   포함**한다(스텁은 1번에서 별도 커밋 완료).

7. **동결 등록(훅+감사 기준)**:
   - 테스트 파일 경로(레포 루트 기준 상대)를 `.cure-implement/frozen-tests.txt`에 한 줄씩 기록 —
     즉시 PreToolUse 훅이 해당 파일의 Edit/Write를 차단한다(예방). **절대 경로로 기록하면 워크트리
     (다른 루트 디렉토리)에서 훅이 매칭하지 못한다.**
   - `git rev-parse HEAD > .cure-implement/frozen-commit.txt` — 감사 기준 SHA. 재동결 시 갱신한다
   - `stub-commit.txt`가 1번에서 기록됐는지 확인한다. **`frozen-commit.txt`와 갱신 규칙이 다르다**:
     감사 기준(`frozen-commit.txt`)은 재동결마다 최신으로 옮겨가지만, RED 기준선(`stub-commit.txt`)은
     「그 테스트가 겨냥한 구현이 아직 없는 상태」여야 하므로 **테스트만 바뀌는 디스퓨트 인정
     재동결에서는 갱신하지 않는다.** 명세 수정으로 스텁 시그니처까지 재파생된 경우에만 새 스텁
     커밋으로 갱신한다
   - `.cure-implement/`는 git-ignored라 이 상태 파일들은 변조 가능하다 — 감사의 불변 기준은 목록
     파일이 아니라 **동결 커밋 자체**다(아래 「사후 감사」 참조)

8. **이후 구현 중 동결 테스트 수정 금지.** **기본 추정은 구현 결함이다** — 동결은 "테스트가 맞다"는
   추정이므로 입증 책임은 항상 구현 쪽에 있다. 수정하고 싶어지면 **직접 고치지 말고 디스퓨트를
   제기한다** → 아래 「이의 제기(TEST-DISPUTE)」의 3분류로 들어간다(테스트 결함은 Codex 판정, 명세
   결함은 사용자 확인). 어느 쪽이든 수정 주체는 하네스가 아니고, 재동결 커밋과 `frozen-commit.txt`
   갱신이 뒤따른다. 훅은 Edit/Write만 막으므로 Bash 우회 편집(`sed -i` 등)은 사후 감사가 잡는다.

## 이의 제기 (TEST-DISPUTE)

구현이 동결 테스트를 통과시키지 못할 때, **기본 추정은 구현 결함**이다. 그럼에도 디스퓨트가
성립하면 3갈래로 분류하고, **분류마다 판정 주체가 다르다**:

| 분류 | 판정 주체 | 처리 |
|---|---|---|
| **구현 결함** (기본값) | — (판정 불필요) | 구현을 수정한다 |
| **테스트 결함** (명세를 잘못 대표) | **Codex** | 인정 시 Codex가 직접 수정 → 재검증 → 재동결 |
| **명세 결함** (수용 기준이 모호·모순) | **사용자** | 확인 대기 → 명세를 먼저 고치고 재파생 → 재동결 |

**테스트 결함만 위임하고 명세 결함은 사람이 잡는다.** 테스트 결함에서 결정되는 것은 「이 테스트가
명세를 옳게 대표하는가」이고, 그 판단의 주체는 명세에서 테스트를 파생한 심판(Codex)이다 — 절차 4번이
이미 "구현 하네스가 assertion을 직접 고치지 않는다 → Codex에 재작성 요청"으로 같은 축의 위임을 하고
있다. 반면 명세 결함은 **명세 자체가 바뀌는 결정**이라, 넘기면 하네스가 자기 계약을 고치게 된다.
`/implement` 경로의 명세는 BE 레포에 있어 **여기서 고칠 수 없다** — BE 쪽 스펙 수정을 확정받은 뒤
재파생한다.

디스퓨트가 성립하면 분류와 무관하게 `⚠️ TEST-DISPUTE` 라벨로 **테스트 이름, 명세 근거, 판단 이유,
분류**를 기록한다. 명세 결함은 이 시점에 사용자 확인을 대기하고, 테스트 결함은 아래 판정으로 넘어간
뒤 **결과를 사후 보고**한다.

### Codex 판정 (테스트 결함)

1. **판정 요청서** — `.cure-implement/<작업 ID>-dispute-prompt.md`에 작성한다. 필수 항목:
   - 대상 테스트 이름과 **실패 지점** — 단언인지 fixture 판별성 가드인지 구분해 적는다
   - **실측 증거** — 재현율(N회 중 M회), 실패 로그, 필요하면 런타임에서 직접 측정한 값
   - **구현 결함이 아니라고 보는 근거** — 명세 인용으로 「현재 구현이 옳다」를 논증한다
   - **인정할 경우 요구사항** — 그 테스트가 검증하려던 동작을 한 문장으로 못박고, 고친 뒤에도
     그 동작이 그대로 단언돼야 함을 명시한다. **이 항목이 개정본 공허화의 1차 방어다**
   - **fixture 공유 제약** — 같은 파일의 다른 테스트가 의존하는 상수·경계값·개수를 열거한다
   - 절대 규칙 3개: **대상 테스트 파일 외 수정 금지**(`app/`·`evals/`·`scripts/` 아래는 한 글자도),
     **어떤 셸 명령도 실행하지 말 것**(검증은 전부 호출측), **판정과 근거를 응답 말미에 명시**
   - **기각 유도 문구 필수** — "이 판단이 틀렸다고 보면 기각하라". 없으면 자기가 파생한 테스트에
     대한 자기 판정이라 인정 쪽으로 기운다

2. **호출** — 「절차」 3번의 4중 hang 방어를 그대로 적용한다(stdin 리다이렉트 · 파일 리다이렉트 ·
   강제 kill 금지 · 산출물 기준 완료 판정). 로그는 `.cure-implement/<작업 ID>-dispute-codex.log`.

3. **판정 sentinel — 3값.** 응답 말미에 아래 중 하나가 있어야 한다:

   | 판정 | 처리 |
   |---|---|
   | `판정: 인정` | 개정본을 「디스퓨트 후 재검증」에 건다 |
   | `판정: 기각` | **구현 결함으로 확정** — 구현 수정 루프로 복귀한다 |
   | `판정: 명세결함` | 하네스의 분류가 틀렸다는 뜻 — 파일 수정 없이 **사용자에게 에스컬레이션** |

   `판정:` 줄이 없으면 실패로 보고 재시도한다. **파일이 바뀌어 있어도 승인으로 해석하지 않는다** —
   완료를 산출물로 판정하는 「절차」 3번 규칙은 파생에만 적용되고, 여기서는 판정문이 산출물이다.
   `명세결함`이 세 번째 값으로 있어야 하는 이유는 **분류를 하네스가 보내기 전에 하기 때문**이다.
   명세 결함을 테스트 결함으로 잘못 분류해 보내면, 이 값이 없는 한 사람 게이트가 조용히 우회된다.

4. **프로토콜 검사(기계)** — `git status`로 대상 테스트 파일 외 무변경을 확인한다. 판정이
   기각·명세결함인데 파일이 바뀌어 있으면 프로토콜 위반이다: `git checkout -- <파일>`로 되돌리고
   사용자에게 보고한다.

5. **라운드 상한 2회.** 초과하면 판정을 멈추고 현황을 사용자에게 보고한다.

6. **Codex 미가용이면 사용자 확인 경로로 폴백**한다 — 하네스 단독 자기 승인은 금지다. 폴백 사유
   (모델 미가용·연속 실패 등)를 보고에 남긴다.

**동결 목록은 건드리지 않는다.** 훅은 하네스의 Edit/Write 도구 호출만 가로채므로 별도 프로세스인
Codex의 수정에는 애초에 무관하고, 목록에 남겨 두면 판정이 도는 동안 하네스의 직접 편집을 계속
차단한다. 제거했다 되돌리는 절차는 노출 창을 만들 뿐 아무것도 얻지 못한다.

### 디스퓨트 후 재검증

동결 게이트(5번 ③)의 **테스트 단위 RED는 스텁 상태에서만 성립**하는데, 디스퓨트 시점에는 구현이
이미 있다. 그래서 「고친 테스트가 여전히 무언가를 죽이는가」를 따로 확인해야 한다 — 그러지 않으면
GREEN이고 결정적이고 범위 안이면서 **아무것도 검증하지 않는** 개정본이 그 검사들을 모두 통과한다.

디스퓨트는 그 위험이 가장 큰 순간이다: 이의를 제기한 쪽(구현)은 테스트가 약해지면 이득이고,
판정하는 쪽(Codex)은 자기 테스트가 틀렸다는 잘 짜인 논증을 받은 상태다 — **두 압력이 같은 방향을
가리킨다.** 네 계층 전부 통과해야 재동결한다:

- ① **범위**: `git status --short`가 디스퓨트 대상 테스트 파일 하나만 보여야 한다
- ② **스텁 재RED**: 개정 테스트를 **스텁 준비 커밋**에서 실행해 실패하는지 확인한다
  ```bash
  SC=$(cat .cure-implement/stub-commit.txt)
  PY="$PWD/.venv/bin/python"
  git worktree add --detach ../dispute-red "$SC"
  cp <개정 테스트 경로> "../dispute-red/<개정 테스트 경로>"
  (cd ../dispute-red && "$PY" -c 'import app; print(app.__file__)')   # 워크트리 경로여야 한다
  (cd ../dispute-red && "$PY" -m pytest <개정 테스트 경로> -rA)       # RED여야 한다
  git worktree remove --force ../dispute-red
  ```
  본 트리의 `.venv`는 이 레포를 에디터블로 설치해 두었으므로 **`app`이 어느 트리에서 import되는지를
  먼저 본다.** 본 트리 경로가 나오면 스텁이 아니라 구현을 검증해 조용히 GREEN이 된다 — 틀린 대상을
  시끄럽지 않게 검증하는 실패다. 단위 테스트는 외부 경계를 가짜로 꽂아 `.env` 없이 돌므로 워크트리에
  `.env`가 없어도 된다.
  개정본이 스텁에서 **import조차 되지 않으면 RED가 아니라 broken**이다 — 구현 단계에서 생긴 심볼을
  테스트가 참조하기 시작했다는 뜻이므로, 자체 판단으로 넘기지 말고 사용자에게 보고한다.
- ③ **본 브랜치 GREEN**: 현재 구현에서 개정 테스트가 통과하는가
- ④ **결정성**: flaky를 사유로 한 디스퓨트였으면 해당 테스트를 **연속 3회** 돌려 전부 GREEN인지 확인한다

### 재동결

재검증 4계층을 통과하면 새 커밋으로 남기고 `frozen-commit.txt`를 갱신한다:
`[TEST] spec <번호> TEST-DISPUTE 인정 반영 — 재동결 (판정: Codex, <판단 사유 요약>)`.
**판정 주체와 사유를 커밋 메시지에 남긴다** — 사람 확인 없이 통과한 경로이므로 히스토리가 유일한
사후 추적 수단이다. 감사 기준은 항상 **최신 동결 커밋**이 되어, 인정된 수정이 사후 감사에서 변조로
오탐되지 않는다. `stub-commit.txt`는 **갱신하지 않는다**(7번 참조).

최종 보고에 `⚠️ TEST-DISPUTE` 항목으로 **테스트 이름 · 판정 · 근거 · 재검증 결과**를 싣는다.
사람 게이트를 없앤 것이 아니라 blocking에서 non-blocking으로 옮긴 것이므로, 보고가 빠지면 이 경로는
추적 불가능해진다.

> **병렬 워크트리 에이전트는 판정 위임 대상이 아니다.** 동시 codex 프로세스가 경합하고, 재동결
> 커밋이 임시 브랜치에 생기며, 스텁 재RED가 워크트리 안에서 또 워크트리를 만든다. 워크트리
> 에이전트는 디스퓨트가 성립하면 **해당 작업의 구현을 중단하고**(커밋하지 않음) **그 작업에
> 의존하는 후속 작업도 함께 중단**한다 — 미구현 스텁 위에 후속 작업을 쌓으면 잘못된 전제 위의
> 구현이 된다. 독립적인 나머지 작업만 진행하고, 완료 보고에 디스퓨트 항목과 중단된 작업 목록을
> 포함한다. 판정·재검증·재동결은 메인 세션이 통합 직후 수행한다.

## 사후 감사

동결이 있었던 모든 실행에서 수행한다. 훅(예방)은 Edit/Write 도구만 막으므로 **Bash 우회 편집은 이
감사로만 탐지된다** — 훅=예방, diff=감사, 두 층이 필요하다.

```bash
FC=$(cat .cure-implement/frozen-commit.txt)
git diff-tree --no-commit-id --name-only -r "$FC"   # 목록 복원 (동결 커밋엔 테스트·fixture만 있다)
git diff "$FC" -- <복원한 목록>                       # 반드시 비어야 한다
```

- 감사 파일 목록은 워킹 트리의 `frozen-tests.txt`(변조 가능)가 아니라 **동결 커밋에서 복원**한다 —
  목록 파일에서 줄을 지우는 것만으로 감사 범위에서 빠지는 순환을 끊는다.
- diff가 비어있지 않으면 **중단하고 사용자에게 보고**한다.
- 워킹 트리의 `frozen-tests.txt`가 커밋된 원본과 다르면 그 자체도 이상 신호이므로 함께 보고한다.
- **감사는 항상 마지막 코드 변경 뒤에 온다.** 수정 루프·디스퓨트 처리가 모두 끝난 뒤 실행하고,
  감사 이후 코드가 다시 바뀌면 **재실행**한다. 감사를 수정 루프 앞에 두면, 우회 편집의 유혹이 가장
  강한 구간(RED가 풀리지 않는 수정 루프)이 무방비가 된다.

## 동결 해제

`.cure-implement/frozen-tests.txt`·`frozen-commit.txt`·`stub-commit.txt` 삭제가 해제다.
**머지 성공 후**에만 수행한다 — 실패로 코드를 재수정하는 동안은 동결을 유지해 테스트를 계속 보호한다.

> **유일한 예외는 폐기다.** `automation/problem.md`가 Phase 4에서 스펙 승격을 판정해 브랜치를 버릴 때는
> 머지 없이 해제한다 — 보호할 구현이 사라지는데 목록만 남으면, 훅이 그 경로들로 **이후 세션의 Edit까지
> 계속 막는다.** 지켜야 할 순서는 「핸드오프 산출 → 해제 → 브랜치 삭제」이며, 그 심판은 미확정 명세에서
> 파생된 것이라 승격 후 `/implement`가 확정된 스펙으로 다시 파생한다.

`.cure-implement/`의 나머지 파일은 성격에 따라 처리한다: `<작업 ID>-test-prompt.md`·`-codex.log`와
`-dispute-prompt.md`·`-dispute-codex.log`는 **재생성 가능한 로그**라 사후 부검(Codex가 짠 RED
테스트가 이상할 때, 또는 인정된 디스퓨트의 판정 근거를 되짚을 때)에 쓰이므로 남기고, 실제 코드
내용을 담은 **데이터 스냅샷**은 목적을 다하는 즉시 삭제한다. `spec-<번호>.md`는 BE에서 다시
조달할 수 있으므로 남겨도 된다.
